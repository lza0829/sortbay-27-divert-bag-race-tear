# 分拣过机台（Sortbay）

骨架：过机扫描装载 → 口门路由裁决 → 错分回流批次 → 封袋班次对账

- 前端 http://127.0.0.1:6600
- API http://127.0.0.1:11600

## 回流 / 入袋争用口径

全局只采用一种架构：**以 SQLite `BEGIN IMMEDIATE` 写锁获取/提交顺序和扫描行 CAS 作为唯一裁决点的“先提交者胜”**。这不是两套架构混用：同一规则按实际提交顺序产生两个闭合结局。
扫描行上的条件更新（CAS）和 `version` 是在途状态登记/第二道裁决，不再使用“先普通查询、后无条件覆盖”的陈旧状态写回。

- **回流抢先提交成功**：扫描成为 `错分回流`，`bag_id=NULL`。后到的入袋 CAS/状态复检失败，整笔事务回滚；不写有效入袋回执、不增袋件数，禁止已回流仍入袋成功。
- **入袋抢先提交成功**：件先落入袋并写有效入袋回执。回流随后必须从 `已入袋` 显式带出该件：清空 `bag_id`、减少袋件数、写 `divert_items.from_bag_id`，并把原入袋回执标记为 `已冲正` 且链接到回流回执。
- **半截失败**：扫描状态、袋/批次明细、回执、审计都在同一个 `BEGIN IMMEDIATE` 事务中；故障抛出后整体回滚。测试用全表快照断言回到争用前。
- **可重放/闭合**：`operation_receipts` 记录入袋/回流回执及冲正链接；`audit_events.detail_json` 记录状态迁移事件。`GET /api/审计/重放` 折叠审计事件并与当前扫描状态、袋件数核对。
- **同刷对账**：`GET /api/总览`、`GET /api/总览/对账`、`GET /api/班次/对账` 共用同一套不变量检查，覆盖扫描状态、袋件数、口门在口、回流批次/明细、有效回执悬空等。

袋件数与口门在口件数不维护可能独立拧花的旁路计数器，而由 `scans.bag_id/chute_id/status` 在同一数据库事实源上聚合。

## 主要定位面

- 回流入口/批次：`POST /api/回流批次`、`GET /api/回流批次`、`GET /api/回流批次/{id}`
- 入袋入口/袋页/封袋页：`POST /api/封袋/{id}/入袋`、`GET /api/封袋`、`GET /api/封袋/{id}`
- 扫描册：`GET /api/扫描` 与别名 `GET /api/扫描册`
- 总览/对账：`GET /api/总览`、`GET /api/总览/对账`、`GET /api/班次/对账`
- 审计/回执/重放：`GET /api/审计`、`GET /api/审计/重放`、`GET /api/回执`
- 前端导航含“总览、过机扫描/扫描册、错分回流、封袋/袋页、班次对账、审计重放”。

## 测试夹具

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r backend/requirements-dev.txt
pytest
```

夹具覆盖：

1. 回流抢先提交 → 并发/后到入袋被拒且袋件数为 0；
2. 入袋先落袋 → 回流批次显式带出，原入袋回执冲正链接；
3. 入袋/回流写了一半后注入故障 → 全表快照回滚；
4. “入袋回执成功却无对应袋件”的悬空回执会被对账捕获；正常争用结局则必须有冲正/回流链接；
5. 真实线程屏障并发多轮，断言最终状态、袋件数、对账与审计重放一致；
6. 所有定位面端点可访问且共享同一平衡口径。

测试专用故障字段 `故障点` 在 `SORTBAY_ENABLE_FAULTS=1`、`TESTING=1` 或 pytest 进程中由 HTTP 入口放行；生产环境默认关闭。服务层夹具可直接传 `fault=`。
